## Confirmed defects and actual corrections

1. **Effective credential reuse**: distinct lone UTF-16 surrogate strings can encode to identical UTF-8 bytes for existing scrypt. Baseline raw-string inequality allowed a claimed successful rotation while the old password still authenticated. The candidate now verifies the proposed password against the current hash and rejects effective reuse before mutation. Existing malformed credentials can still authenticate and rotate to a genuinely different password. This is a credential-rotation correctness defect, not a scrypt break or account takeover proof.
2. **Silently missing required audit insert**: an owned privileged failure-injection trigger returning NULL caused create to return without an event, while credential/revocation committed and HTTP 200 was returned. The transaction now rereads the generated exact event ID and checks actor/action/revoked count; failure rolls back with 500.
3. **Silently unchanged credential write**: a privileged failure-injection trigger returning OLD allowed update count 1 without changing the hash. Baseline revoked sessions and returned success. The transaction now rereads the effective stored hash and requires the derived replacement before continuing. Failure rolls back with 500.

The latter two require schema-level fault injection; no remote caller can create these triggers. They are confirmed atomicity/readiness defects under required-write failure, not independently exploitable anonymous vulnerabilities. The bounded fixes protect the claimed application contract, not against a malicious database owner capable of falsifying all reads. Baseline and corrected response/state summaries are retained under `security-evidence/` without credential values.

`tests/account-password-review.integration.test.ts` proves all three through real HTTP and persistence; `tests/password-change.integration.test.ts` retains original race, expiry, exclusion, revocation, audit failure and session-failure checks. No global password policy, login algorithm, session cookie, Support identity or authorization changes are introduced. `lib/auth.ts`, login route, worker, schema, lockfile and historical migrations remain byte-identical to baseline.
