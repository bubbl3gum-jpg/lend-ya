# Existing architecture and 11E candidate policy

27 October 2026, Asia/Taipei. Clean baseline `e9636b7c2150f17ed3952c41600fd6217eacd5d2`, verified 11D implementation `1866016dc5891cd90c9472e4ff8895024d275ea9` and evidence `d2fd4ce6ed85b4b6a6e1d68b2fba9820283365f7` ancestry. Isolated branch: feature/authenticated-password-change-batch-11e.

## Audited existing contracts

- `lib/auth.ts`: existing salted scrypt (16-byte random salt, 64-byte key) and timingSafeEqual verification; existing password parser accepts raw JS strings (registration 8–128 code units, login 1–128), with no trimming/normalization. Reuse these functions, not another password system.
- AuthSession persists SHA-256 token hash, user, createdAt/expiresAt; random 32-byte cookie token, seven-day lifetime, HttpOnly/SameSite=Lax/production Secure. getCurrentUser reads real session and deletes expired sessions. Logout deletes current row; no credential version column exists.
- Existing login verifies a password before creating a session. That separate issuance could race a credential change and mint a stale session after revocation. Both ordinary login and the owned Support worker reverify/issue; registration creates a new unique user/session atomically. Centralize verified-hash comparison and a transaction advisory lock for the two login issuers; do not change hashing, suspended-login behavior, role grants or cookie policy.
- `lib/auth-rate-limit.ts`: persisted per-email login (10) / register (5) attempts per 15 minutes; no trust in caller-forwarded IP headers. Existing limits remain unchanged.
- Proxy checks explicit wrong Origin/cross-site mutations but permits a missing Origin for legacy routes. The new endpoint additionally requires exact configured Origin, matching request URL origin, application/json and X-Hustlen-Password-Change:1. Strict Origin plus nonsimple custom header and existing SameSite cookie provide the candidate CSRF boundary; no broad proxy relaxation or production CORS change.
- `app/api/account`: existing authenticated name-only editing also permits suspended accounts. No password endpoint exists at baseline. Forgot-password does not deliver recovery. Activity/trust queries are unchanged.
- Staff MFA assurance/challenges are bound to persisted AuthSession id/incarnation; deleting every AuthSession invalidates that authority without rewriting historical MFA evidence. New sessions never inherit assurance. No staff or passkey credential is provisioned/revoked here.

## Explicit candidate policy (not production approval)

Only NODE_ENV=development + independent owned-password-only gate + exact disposable database/driver target + matching harness database ownership comment/run ID + exact localhost origin + allowlisted trusted user ID. Production refuses even with the flag configured. Ordinary USER accounts only, ACTIVE or SUSPENDED, no StaffAccountAssociation or ChatReviewer. Admin/staff/reviewer password changes are deliberately unavailable pending their MFA/security policy; never grant a broad ADMIN shortcut. Suspended users may secure credentials without restoring marketplace authority or changing existing rental/return/Support obligations.

Require valid current session and current password, a different 8–128-character new password and exact confirmation. Reject all URL query selectors and unknown payload fields/actor IDs; bounded existing 32KiB streaming JSON reader, exact three-string schema. No password trim, translation, request-body logging, hash display, secret browser persistence or email claim. Candidate limit: five authenticated attempts per account per 15 minutes, persisted atomic UPSERT with capped counter and expiry; includes malformed and wrong-password attempts after authentication, survives process restart, fails closed on storage failure or a missing/invalid persisted counter result. No unrelated global counter cleanup or caller-controlled IP trust. Production needs reviewed ingress/abuse policy.

Use server-resolved user/session only. Verify current hash outside the credential transaction, derive new hash with existing scrypt, then acquire the shared user advisory lock and User/current-session row locks. Recheck current session against database clock again after lock acquisition, eligibility and exact verified hash; CAS update. Delete all user sessions (including expired/current/other-device), verify none remain, and insert minimal immutable AccountSecurityEvent in the same transaction. Any failed credential/session/event operation rolls back all three. Attempt counter is intentionally independent and not rolled back. Concurrent changes cannot both win. Login compares its exact server-verified hash under the same lock before issuance: login first is subsequently revoked; password first makes stale verified-hash login fail. Response loss cannot make deleted sessions valid again.

Success clears the cookie and returns only changed/reauthenticationRequired booleans. All previous sessions are invalid; require genuine fresh login with the new password. UI clears password fields after every real attempt, hides stale account metadata and disables name submission after revocation, but retains the unrelated name draft in a keyboard-selectable read-only input for copying. It offers a full-document sign-in link rather than silently discarding that draft. No automatic retry of ambiguous failures. Browser password memory is necessarily present while typing; no claim of guaranteed JavaScript memory erasure or control over user-managed password managers.

## Audit/migration and production gates

New additive forward-only AccountSecurityEvent table: server UUID, trusted actor FK, fixed PASSWORD_CHANGED action, positive revoked-session count and database clock timestamp. No arbitrary JSON, passwords/hashes/tokens/session cookies/bodies. UPDATE/DELETE/TRUNCATE triggers reject mutation; a database owner can still alter schema, so production least privilege/retention/evidence governance remains required. Existing histories/migrations are unchanged. No backfill or automatic ADMIN promotion. Migration tests run only on fresh owned databases; never migrate existing application databases here.

No notification was sent or queued. Out-of-band delivery/provider/outbox, retention/access policy, rollout and ordinary/staff credential policies require separate approval before production. Recovery remains distinct: enumeration-safe intake, real approved delivery, hashed single-use purpose-bound expiring tokens, concurrent/replay protection, revocation/audit, notifications and separate privileged identity recovery. No reset/email-link/reassociation endpoint is added.

In-flight requests already authorized before commit cannot be retroactively erased by this endpoint. This batch prevents stale session issuance and subsequent protected authentication, and preserves corrected meetup polling. A whole-application mid-request revocation/authorization cutover requires separate review; do not claim universal cancellation of already-running operations.
