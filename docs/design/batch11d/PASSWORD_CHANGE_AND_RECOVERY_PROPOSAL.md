# Password change and recovery — decision proposal, not implementation

Engineering threat review for the next Stage 9 decision. Product/security sign-off is pending. No new endpoint, password UI, recovery delivery, identity reassociation, staff provisioning or session policy is activated by Batch 11D.

## Genuine authenticated change (recommended next bounded implementation)

1. Resolve the exact current persisted AuthSession and User server-side; ignore browser user/session/role/assurance selectors. Reject expired/deleted sessions. Define whether a suspended account may secure its credentials without removing restrictions or access to existing rental/return/support obligations; do not infer it from display-name permission.
2. Require current-password verification using the existing password verifier and constant-time comparison. Existing Admin MFA/staff-assurance requirements must be honored independently; a password change is not staff authorization or recovery. Never accept email-only, pending assurance or synthetic MFA as proof.
3. Apply strict same-origin/CSRF controls, bounded JSON parsing, explicit field allowlist, current/new password length rules consistent with the verifier, compromised-password policy if approved, and server validation. Never trim/normalize passwords silently. Do not store draft credentials in URLs, cookies, local storage, analytics or logs.
4. Proposed abuse limits for review: per-account and per-trusted-network-source sliding-window attempt bounds, distributed atomic enforcement, backoff, safe generic responses and no durable account lockout an attacker can trigger. Exact counts/windows, trusted-proxy rules, retention and unavailable-limiter fail-closed behavior need approval; existing in-process limits alone must not be presented as multi-instance protection. Current-password failures must not disclose foreign account existence.
5. In one transaction, recheck current session validity and compare the current credential hash/version to the reauthenticated snapshot, update only that User credential, revoke other sessions, rotate the current session to a fresh incarnation (or revoke all and require login if that policy is selected), and append a minimal attributed security event. A concurrent password update must cause conflict/reverification. An old hash/password/session cannot win a stale race. Do not add a broad generic account-status editor.
6. Recommended revocation: all prior sessions, including current old token, cease authorizing; issue the rotated current token only after the transaction succeeds, using existing secure cookie attributes. Decide explicitly how session-bound MFA assertions/challenges become stale and whether credential changes revoke existing assurance. Do not transplant old session assurance. Do not alter historical booking/evidence/custody records or create staff grants.
7. Atomic audit failure aborts credential/session changes. A post-commit response/notification failure must not roll back security or pretend the old password still works. Define safe retry: client receives clear sign-in/reverification guidance; no replayed current-password payload stored for idempotency. Use nonsecret error IDs and bounded event fields, never passwords/hashes/tokens/full requests.
8. User notification requires a real approved provider and template, durable outbox/retry and minimal delivery metadata. Notification failure must be visible operationally; do not claim a message was delivered from console output or a successful enqueue alone. Notification action links must not weaken authentication.

## Recovery is separate

Lost-password recovery needs a separately approved flow and delivery service: enumeration-safe intake, cryptographic single-use hashed bounded-expiry tokens, purpose/account binding, atomic use and revocation, replay/concurrency protection, rate limiting, secure new-password setting, session/assurance revocation, audit and honest notification status. No security questions, password-only staff recovery, email-only privileged identity reassociation or self-approved administrative recovery. Passkey loss and verified-human/staff association recovery require their existing independent-human governance; ordinary marketplace reset cannot bypass it. The existing forgot-password stub remains truthfully unavailable.

## Decisions and release gates

Approve the endpoint contract, suspension policy, password rules, exact rate limits/storage/outage behavior, current-session rotation vs total logout, MFA invalidation, event retention/access, real delivery provider/outbox and recovery policy independently. No migration should modify an existing database without separate authorization. Use additive reviewed migrations and newly owned fresh/populated fixtures when needed.

Required tests: anonymous/forged/expired/deleted/suspended-session boundaries; wrong current password; reused/oversized/malformed values; CSRF/wrong Origin; rate limit/concurrent attempts/outages; stale credential race; transactional audit failure; session rotation and old-session invalidation across browsers; MFA challenge/session binding; replay and response-loss handling; actual provider sandbox delivery and notification retry; no credential leakage; unchanged name editing, legacy Admin/ChatReviewer, staff/approval guards, rentals, Support and real-camera meetup. Recovery adds token expiry/replay/enumeration and independent reviewer tests. Preserve deadlines and record first failures.

Recommendation: decide secure authenticated password management next, with recovery remaining a separate gated scope. Run accessibility closure in parallel planning only; do not move into Stage 10 AI while Stage 9 security, real-device and owner acceptance questions remain unresolved.
