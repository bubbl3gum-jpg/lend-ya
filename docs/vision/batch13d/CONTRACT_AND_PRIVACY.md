# Documentation, quality and future Vision contracts

## Version and provenance

`lib/item-documentation/checklists.ts` pins candidate definitions at version1, returns clones, and uses exact actual category keys (`Cameras`, `Tools`, `Camping & Outdoors`); unknown/prototype/unsupported keys get general guidance. Views differ: camera body/optics/mount, tools housing/working-end/power interface, camping fabric/structure/closures. Relevant wear, actual accessories and safe functional checks are explicit. A photo never proves a functional check or accessory presence.

These are development candidate requirements, not retroactively enforced historical rental requirements. Future new versions must retain prior definitions and persist the selected checklist ID/version and applicability with the rental pickup baseline; return must use that same baseline version. Current legacy photos have no such mapping, so the prototype never infers it. No production publication or pickup/return requirement is changed.

Listing photos, HANDOFF_OWNER/HANDOFF_BORROWER, RETURN_BORROWER and INSPECTION_OWNER retain their original stages, authorship, booking and server timestamps. Pickup is primary rental-condition baseline; later inspection is supplemental, not a replacement. Existing authenticated byte endpoints remain the authority. Actual QR/receipt events are separate from any photo: an image's existence or INSPECTION status does not establish verified custody. The existing 13B summary supplies a return timestamp only when its completed challenge/explicit receipt checks succeed. The new read-only pickup status similarly requires matching participant event/completed consumed pickup challenge plus bilateral handoff acknowledgment. Neither a staged photo nor a timestamp alone proves verification; legacy/absent receipts stay null. These are application acknowledgments, not real-MRT arrival certification or forensic image proof. Server-recorded time is not forensic capture attestation.

## Owner preview and quality

An actual listing owner in the verified owned development database selects/captures one still photo for each candidate area, declares wear and accessories, reviews the information and explicitly checks confirmation. Missing views/incomplete declarations disable review; server independently rejects missing/duplicate/unknown area mappings, unsupported fields, invalid revisions and unconfirmed/bounded text. Existing listing conditions/media remain untouched. No live listing auto-publication, new persistent document or real confirmation/audit is claimed.

The streamed multipart bound is20MiB+32KiB, at most the registry's required views, existing max5MiB/photo and20MiB total. Existing `validatePrivatePhotos` actually decodes still JPEG/PNG/WebP, validates format/MIME, dimensions/animation and strips metadata via re-encoding. Inputs are transient; no file, DB row, local storage or remote upload is created by the new service. Decode buffers are released to garbage collection after request; no claim of forensic memory erasure. Browser object URLs are revoked on replacement/record change/unmount; no images in logs. Only item photos permitted by notice; no reliable classifier exists to identify whether a user selected an inappropriate personal image. Do not supply real identity/face material.

Hints use a bounded128×128 greyscale sample of the sanitized decoded image. Mean<35→DARK, mean>225→BRIGHT; mean absolute horizontal/vertical neighbour difference<3→LOW_DETAIL; short decoded side<640→SMALL. Thresholds are fixed candidate heuristics, not AI, reliable blur detection, readability/coverage certification or calibrated camera recommendations. A smooth surface can trigger low-detail and a sharp/bright irrelevant photo can pass every threshold. The UI supplies actionable retake guidance without claiming a condition finding. Dimensions refer to the metadata-stripped decoded/resized image, not necessarily the original device file.

## Gate and resource authorization

Independent production proxy and service refusal, even with candidate flag. Development additionally requires exact HUSTLEN_DOCUMENTATION_CANDIDATE=`owned-preview-only`, matching safe local owned-test URLs,24hex run ID and actual DB name/ownership marker. Existing valid current session; no new role grants. Own listing only; participant booking only. Active account required for new owner preview, while suspended participant reads preserve existing obligations. Re-resolve actor and own resource after image decoding; stale revision409, revoked session401, lost ownership404. This does not cancel every previously authorized request universally.

POST requires exact configured localhost URL/Origin, custom X-Hustlen-Documentation:1 header and non-cross-site multipart. GET allows exactly kind/id; no user, role, evidence URL, Support/case or provider selector. DTO is private/no-store/Vary Cookie. No raw request/file logs; bounded operational error context only. Source/bytes remain on existing protected routes; unrelated ADMIN/Support membership adds no access. UI aborts old requests and fences aborted results; focus rechecks current authentication without treating a file chooser's focus change as session loss. No background polling loop.

## Future inference only

`vision-contract.ts` defines authorized evidence references with source/author/time, category/checklist ID/version, area-linked QUALITY/POSSIBLE_DIFFERENCE/ACCESSORY_UNCERTAIN/RETAKE observations, uncertainty/confidence and UNAVAILABLE/FAILED states. Current runtime always UNAVAILABLE, observations empty. No adapter, credential, endpoint, SDK, inference, provider/image transmission or billable processing.

Structural validation requires exact keys, known area, bounded text/uncertainty/confidence and allowed source refs; it rejects financial/action extensions. It is **not** factual grounding, identity, causation, authorization or safe natural-language certification. Future authorized service must build references through existing resource authorization, minimize image export, enforce provider/privacy/retention policy, preserve immutable originals and require human review. No reliable damage valuation, guilt, deposit deduction or autonomous decision.

Local reviewer notes are unsent, bounded and cleared on record change/leaving. No structured model result is fabricated from these notes. Optional capture via native file input is not the fresh rental evidence flow and cannot bypass existing actual camera/QR/GPS/consent/physical receipt.
