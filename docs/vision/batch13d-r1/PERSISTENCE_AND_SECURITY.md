# Durable studio persistence and security contract

## Additive model

Only four new candidate tables, no historical row changes or backfill:

- DevItemDraft: one owner/listing draft, pinned category/checklist definition, bounded structured data, revision and database timestamps. Partial text/photo drafts allowed.
- DevItemPhoto: immutable sanitized bytea using the existing private BookingEvidencePhoto convention; owner/listing/area/revision, original input SHA256, stored-byte SHA256, computed quality, database source time and fixed OWNER_SELECTION_NOT_RENTAL_EVIDENCE provenance. Original unsanitized bytes/EXIF/file names are not stored. Input hash is provenance metadata, not proof of device/capture authenticity. These are not rental evidence rows.
- DevItemVersion: immutable owner-confirmed copy of draft facts, checklist definition/version, protected refs, listing/owner/revision, source creation time and database confirmation time. Owner assertion, never machine verification or rental agreement. Further edits change only the draft.
- DevItemEvent: immutable attributed SAVE/PHOTO/CONFIRM event with prior/result revision, optional confirmed-version FK and database time. No raw request/error/file payload in events.

Migration `20261028160000_owned_item_documentation` creates these tables atomically in an explicit PostgreSQL transaction, with FKs, bounded constraints, owner/development guards and deferrable atomic-history checks. It modifies no old migration. New User/Listing reverse relations in Prisma do not assign authority or alter existing record values. No production deployment is authorized. Historical listings with no draft remain empty/unknown. Existing records are not converted.

DB guards require actual local test database naming/ownership marker plus transaction-local studio/actor settings and actual ACTIVE listing owner. Draft category/checklist/creator/time cannot be rewritten; revisions advance exactly1. Photos/versions/events reject UPDATE/DELETE. Populated history also rejects TRUNCATE (empty fixture tables may truncate safely). Deferred constraints require the matching event for every draft/photo/version write; version snapshots must exactly match confirmation revision/facts/checklist/source time. Primary/unique keys prevent duplicate revision history. Superusers able to disable triggers remain outside application threat controls; this is not a claim against arbitrary privileged SQL administration.

## Service boundary and atomicity

`/api/dev/item-studio` and protected `/photos/[id]` refuse production independently of flags. Development requires exact owned-studio-only flag, matching three validated local test URLs, run ID and actual database name/comment, then existing persisted session. Browser identity/roles/policy/version attribution are never trusted. There is no Staff/Admin OR fallback.

Writes require exact configured localhost Origin/URL, custom X-Hustlen-Item-Studio:1 header, no cross-site request and closed JSON/multipart fields. All writes serialize on the owner advisory key, then lock the owner account before the actual session row (matching credential-revocation account/session ordering and serializing logout deletion), then the listing before revision checks. ACTIVE account/owner and current unexpired session are checked in the transaction after image decoding. Suspension and new writes serialize through account lock. A previously authorized transaction may finish before logout obtains its deletion lock; later requests are denied. This is not universal cancellation of all already-authorized operations.

Photo-first creates a real draft with its first saved photo. Manual-first saves partial fields then adds photos to the same draft. Existing text must be saved before photo addition, avoiding silent replacement of dirty text. One update and one event per transaction; failure of required event/constraint rolls back photos, facts and confirmation. No console-only audit. Expected revision conflicts409; no silent lost update. Lost-response retry with an old revision returns conflict and caller reloads recorded history; it does not create a duplicate confirmation. This is not a general idempotent submission framework.

Limits:30 drafts/owner;200 revisions,24 protected photos and20 confirmed versions/listing. Draft condition/defects each2000chars,12 accessories with120char names/40char quantities,4 area refs, total encoded payload<16000bytes. Accessory declarations INCLUDED/EXCLUDED/UNSPECIFIED and visibility DOCUMENTED/NOT_VISIBLE/UNCLEAR are independent. DOCUMENTED requires an own selected photo ref; other visibility states cannot fabricate a reference. Participant-reported missing is a separate future rental report type, not an owner-editable missing flag. Non-visible never becomes missing.

Exact own listing/area/media references are checked server-side; a source photo cannot be reassigned to a different area or foreign listing through save input. Confirmation requires saved condition/defect statements, an explicit overall accessory statement (NONE, or DECLARED with named/quantified entries), complete required views and explicit human confirmation. NOT_SPECIFIED remains a saveable incomplete draft; NONE is explicitly selected, never inferred from an empty list. Photo content/applicability is not machine validated; no automatic model/type/accessory inference.

## Media and retention

Reuses validatePrivatePhotos: real still-image decoding, MIME match, animation/pixel/size/resource limits, metadata-stripped re-encoding. Per-upload streamed5MiB+32KiB maximum, one file <=5MiB. Existing bounded image hints retained and translated; no reliable blur/coverage/authenticity/damage claim. Stored metadata includes source and stored hashes without storing raw originals. Protected bytes require a current authenticated owner who still owns the listing; no unrestricted URLs, public media writes or automatic borrower sharing. Read headers private/no-store, nosniff and same-origin/sandbox.

The development history intentionally retains superseded media to preserve confirmed references; it is bounded and cleaned by dropping only its verified owned disposable database through the harness. No app delete/purge or production retention policy is invented. Future production retention/holds/deletion, ownership transfer, account deletion and FK compatibility require review. New RESTRICT relationships may intentionally prevent deleting a candidate listing/account containing preserved documentation; production tables remain empty/unactivated until a separate rollout.

## UI / inspection / agreement

Both entry paths share persisted records; language switching changes only labels. Dirty text and selected unsaved files are identified; beforeunload warns, and changing records asks before discard. No fake last-saved time. Confirmation operates on saved facts only; new revisions do not publish/reactivate anything. Saved history/quality/photos reload across sessions and page reload, not localStorage or session-memory authority. New operational strings are English/Traditional Chinese; original user text, IDs/event codes stay unchanged. Existing heritage materials/preferences remain; no model effects/sounds.

Existing 13B viewer and13D comparison can read a reusable saved-documentation panel only under the independent studio flag/resource checks. Current owner-confirmed listing facts are labelled NOT agreed rental terms. Borrowers receive no unagreed private owner history/media. The agreed-rental section is explicitly UNKNOWN; fresh pickup, return and later inspection remain separate and unchanged. Legacy source-area mappings are not invented.

`agreementAdapter()` is intentionally no-write/idempotently blocked. Existing booking request/acceptance lacks borrower-reviewed documentation ID/hash and same-proposal consent. An independently approved agreement extension is required before a new test rental can bind a version. No competing endpoint guesses 'latest', silently backfills old bookings or substitutes a listing confirmation for physical pickup evidence. Precise blocker in pre-implementation audit.

Still blocked: actual claim/borrower response persistence, qualifying delivery and enforceable 48h deadlines, exceptions/appeals, settlement/financial deductions and production dispute cutover (named 13B-R1 dependencies; no separate artifact at baseline). Canonical 24h inspection/48h response durations unchanged. No eKYC/Vision provider, biometric processing, production participation/publishing gate, staff access or Stage 11 automation.
