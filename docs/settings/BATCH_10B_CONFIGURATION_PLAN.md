# Batch 10B — typed configuration implementation plan (proposal)

No operational setting mutation is authorized by Batch 10A. Start with review of `lib/admin/settings.ts` and the source inventory, not a replacement global configuration table.

1. **Approve exact identifiers and owners (S–M).** Select only clearly display-only routine settings first (for example a new Admin directory page-size preference, if separately approved). There is currently no approved mutable operational key. Establish code-defined closed schemas, scalar types, bounds, scope, dependency list, default/fail-closed semantics, authority and risk. Unknown identifiers denied. Secrets and infrastructure bindings are excluded, not editable “high-risk values”. Security-critical invariants never enter the registry.
2. **Additive persistence and read adapter (M).** Proposed ConfigPolicyVersion, ConfigProposal, ConfigRevision and append-only ConfigEvent with bounded typed values; unique identifier/scope/version and compare-and-set. Retain each current source as authoritative until that identifier's migration is reviewed. No generic JSON patch/SQL/environment editor. Include source/hash and effective version in minimal DTOs. Invalid/unavailable policy yields explicit unavailable and prevents dependent privileged actions; never silently relax a check.
3. **Routine configuration slice (M).** Only approved narrow routine capability; authenticated server-loaded identity and scope, exact schema, versioned proposal/event, atomic execution and idempotency. Preview actual impact. Rollback is a new validated version, never history deletion. A display preference must not alter rental/GPS/evidence/auth policies.
4. **High-impact proposal foundation only (M–L).** Bind value, ID, scope, old/effective policy version, dependency digest, risk, reason, expiry and actor to the exact proposal. Independent authorized human cannot be requester, investigator/conflicted participant or an alias of them. Existing Batch 4 foundation is not live execution authority. One-person/small-team absence blocks execution rather than bypassing separation. Recheck approvals, real MFA, authorization versions, current config and dependencies under locks immediately before atomic write+event; fail closed on audit/approval outage.
5. **Consistency and rollback (M–L).** Start with no cache and DB transaction reads where suitable; if caches are approved, versioned keys plus durable invalidation/outbox, TTL and stale-read refusal. Test multi-process races, rolling deployments and old reader compatibility. An acceptance proof must record the exact policy version, not read a silently changing singleton. Changes to custody/GPS/evidence/auth/payment need separate end-to-end source migration, proof invalidation and rollback design; never route them through routine writes.
6. **Security gates and stop (M).** Fresh and populated owned migrations, unknown key/type/range/forged risk denial, stale approval/version/cache, conflicting edits, audit failure, idempotency, rollback, alias conflicts, unauthorized fields, secret exclusion and full existing regressions. Independent review before any production migration, new role activation or settings editor rollout.

Announcement follow-up is separately scoped: approve audience and routine publisher policy; keep high-impact publication blocked until exact approval/execution controls are reviewed. If external delivery is approved, implement transactional outbox and explicit delivery state without claiming that server visibility implies delivery. Retention/localization and recovery policy decisions precede rollout. Do not bundle Support activation, real Operations provisioning, AI or financial controls into configuration management.
