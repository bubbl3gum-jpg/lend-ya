# Pre-implementation audit — 29 October 2026, Asia/Taipei

Clean baseline `748698710a1e9b98eb43b6e3d4f11f0577a53003`, branch `feature/durable-disputes-responses-batch-13b-r1`. Supplied implementation `a6c8705e78fa0948210e23a9b6f940f711f55e9c` and closeout `28145c4263b5a97341d4639005e44447c24c732a` are ancestors. Isolated branch `feature/resolution-room-mutual-recovery-batch-13e`.

`Dispute` remains authoritative case/status, `Booking` actual participants/terms/lifecycle. `lib/condition-claims/service.ts` and its original booking dispute endpoint supply real typed owner claim, exact accepted R2 context and immutable participant response, subordinate revision/event history and original borrower notice. Original24h owner submission/supplement rule and non-enforceable synthetic48h clock are not recovery-plan rules and must not change.

`lib/inspection/service.ts` derives actual verified physical return from receipt/challenge/bilateral evidence. Saved DevConditionClaim retains it; opening/agreement in a room must not create a new receipt, call handoff/return writers or reverse custody. Original `/api/bookings/[id]/evidence/[photoId]` is the private byte authority. R2 actual booking documentation stays immutable, never selected by latest listing version.

Existing Conversation/ChatMessage/outbox are booking discussion with established eligibility, moderation/read state and delivery behavior. Support channels have separate private assignment/action/assurance and audit rules. Do not copy either transcript into the shared case or grant staff access. New room discussion can be narrowly subordinate, fixed-kind case coordination events, not a competing dispute identity or general messaging service.

Existing DevConditionNotice is the durable case notification root, initially borrower-scoped. Its created/queued/viewed semantics are reusable, but adding room actions to DevConditionEvent would incorrectly consume claim revision quotas or bypass original supplement restrictions. Introduce separate subordinate room activity notices linked to that existing notice root, with exact recipient and immutable view acknowledgements. No delivery worker/real receipt exists; no48h activation.

Proposed minimal extension: one room per existing structured dispute; immutable proposal terms and append-only attributed events with bounded room revision/idempotency. One unresolved offer, counterproposal explicitly supersedes pending predecessor, accepted plan frozen and completion pending. Expiry applies unanswered offers only; acceptance is counterparty-only and cannot execute recovery. Shared discussion is not amendment/evidence submission. Future Support/AI remains scoped approval-dependent, no new access or inference.

The messaging audit also found that `lib/chat/service.ts:permitted` refuses free-text contact for either suspended account or UserBlock, and `lib/chat/policy.ts` supplies deterministic moderation. Room free text/new offers/acceptance must not bypass those restrictions. Candidate uses sorted participant account locks, existing block/account checks and conservative ALLOWED-only text screening; historical reads, reject/withdraw, view acknowledgement and assistance intent remain available. Formal13B-R1 response and rental obligations are unchanged.
