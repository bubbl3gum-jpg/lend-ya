# Ticket intake / own-status candidate contract

Baseline `1d921d2f42e6137266877e2d2f5c48997a71e2b4` (clean Batch 8A). Branch `feature/customer-service-ticket-intake-batch-8b`. See [policy mapping](SUPPORT_TICKET_POLICY_MAPPING_BATCH_8B.md) for the mandatory production gate. No Support Agent/staff identity or operational recovery is activated.

## Schema and integrity

`prisma/schema.prisma` adds SupportTicket and SupportTicketEvent, plus inverse relation fields on existing User/Booking/Listing/ListingReport/Dispute models. Those existing tables gain no storage columns or data updates. The new forward migration `20261025090000_support_ticket_candidate/migration.sql` adds only candidate tables, FKs, indexes/functions/triggers. All 23 earlier migration files remain unchanged. Prisma explicitly models the FKs and composite keys; CHECKs, trigger behavior and deferred constraint timing are authoritative SQL and are separately tested. No production database was migrated.

SupportTicket: server UUID; requester User FK; fixed category/policy; subject 1–120 and description 1–2000 trimmed JS code units (conservative relative to DB character limits); RECEIVED currentState; lifecycleVersion=1; UUID requestKey; SHA256 normalized-content requestHash; initialEventId; at most one nullable booking/listing/report/dispute FK; database timestamps. No actor/role/status/time/policy/assignment is accepted from a browser. No migration copies existing reports/disputes or narratives. Existing model relationships enforce real ownership; merely existing IDs or shared booking membership do not grant ticket reading.

SupportTicketEvent: server UUID, exact ticket FK, authenticated actor User FK, fixed TICKET_RECEIVED, sequence/version=1, correlation=requestKey, DB timestamp. Two deferred composite FKs bind ticket, actor, initial event, key and version in both directions. A transaction cannot commit a ticket without its required matching event, share another ticket's event, forge an event actor or independently append a status transition. Unique `(requesterUserId,requestKey)` and `(ticketId,sequence)` enforce concurrency. Initial timestamps are DB-assigned and caller timestamps cannot override them. Immutable update/delete/truncate triggers apply to both tables. No retention-delete bypass exists.

Creating within one transaction locks the authenticated User row, rechecks ACTIVE, returns a content-bound same-key replay or rejects conflicting reuse, checks typed relationship eligibility and candidate quota, then creates ticket+event. Failure rolls back both. CurrentState cannot be a user-editable generic status; all fields are immutable in this candidate. Version 1 is an intentionally bounded foundation, not a claim that future transitions already work. Ticket lifecycle facts are not staff-security access audits or case-resolution/custody records.

## Services, endpoints and DTOs

`lib/support/tickets.ts` is server-only. `ticketContext` independently checks trusted environment/effective target/ownership marker, real server session, ACTIVE status and trusted requester allowlist. This happens at every service boundary, not just HTTP. No ADMIN OR SUPPORT_AGENT fallback, automatic staff activation, identity verification claim or MFA assurance is introduced.

- POST `/api/support/tickets`: exact allowed JSON keys categoryCode, subject, description, requestKey and one optional typed FK. 32 KiB body bound, fixed category/text/UUID/integer validation. Requester is never a body selector. Returns 201 for first create, 200 replay, 409 conflicting content, 429 candidate quota. Creation DTO: id, categoryCode, subject, currentState, createdAt, lifecycleVersion and replay flag. No secret hash/key, actor or copied evidence is returned.
- GET `/api/support/tickets`: no filter except page 1–10000; fixed page size 10; exact requester predicate in findMany AND count, repeatable-read snapshot. Newest `(createdAt DESC,id DESC)`. Returns own items/page/pageSize/total, not other-party counts. Offset pages can shift under concurrent creation; fixed-data tie ordering is deterministic.
- GET `/api/support/tickets/[uuid]`: requester is part of the database WHERE, before reading content. Foreign and missing UUIDs both return 404, including for legacy ADMIN. Own DTO adds description, authorized related kind/ID or null, and fixed eventType/sequence/createdAt history. A related link is checked again at read time; if its eligibility changed, it is omitted. Own submitted content remains own content. Report/dispute references are labels, not links to broad Admin endpoints. Booking/listing links apply existing independent authorization.

Mutation Origin and Host must match the trusted exact localhost origin, JSON content type is exact, absent/wrong POST Origin and cross-site requests are refused; proxy protection remains independent. Unknown query/body/actor/role/evidence selectors are rejected; UUIDs/IDs alone are not authority. Responses and dynamic ticket pages are private/no-store with Cookie variation. Error responses use fixed safe messages and bounded operational error IDs, not raw database errors or submitted content. Existing sensitive-data logging remains unchanged and no new success log records ticket text. Required creation-event failure is fail-closed. Console logs are not represented as durable private-ticket access audit.

## Customer Service UI

Existing guidance and reporting/dispute support rights remain. The isolated pilot provides Create ticket, My tickets and own detail pages, all independently guarded. Native labelled controls provide category, bounded subject/description, optional typed record+ID (both or neither). Client request key persists across network retries and resets on intentional content/relationship/category changes; disabled submit prevents a parallel click. Only actual successful server response navigates to the canonical UUID. Own list has bounded pagination, actual states/categories/time/reference; detail shows original submitted text, authorized reference and DB-recorded initial history. No staff-response/assignment indicator, attachment control, status editor, notification delivery or recovery action exists.

Production candidate routes are 404 even with the flag configured; no ticket form is shown on the production help page. Free text is not a DLP engine: fixtures must be synthetic, the form warns against credentials/IDs/private chat/evidence/coordinates, and no production policy is inferred from that notice. No marketplace transcript, private evidence or ID document is selected/imported by the intake services.

## Admin and historical compatibility

The Community Support workspace remains a report/dispute directory, explicitly not a private SupportTicket reader. Its query/DTO/guards and the broad legacy audit directory are unchanged; a static clarification does not reveal any ticket's existence. No Admin ticket viewer is authorized in this batch: scoped access plus durable audit approval is still missing. Ownership predicates also deny the shared booking's other participant, moderator, unrelated user or legacy administrator from private ticket content.

Historical fixtures verify User/AuthSession, Report/Dispute, booking/handoff/return/evidence, chat/reviewer/audit data and migration rows/checksums. The exact old Batch 8A Prisma client still reads those records after upgrade. Failure injection rolls back new DDL; explicit owned-test rollback resolution applies exact reviewed SQL; replay is a no-op. Combined Prisma schema diff remains empty, including FKs and composite unique keys. No direct runtime principal grant/RLS activation is added; future staff channels require the stronger separately reviewed boundary, not reuse of legacy broad DB/API authority.
