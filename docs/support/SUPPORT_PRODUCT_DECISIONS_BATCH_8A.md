# Customer Service product decision register — Batch 8A

Approved principles are those explicitly authorized by the product owner. Proposals below are choices for review, **not approved production defaults**. Existing legacy report/dispute behavior is preserved without treating it as the policy for a new generic ticket system. No synthetic fixture establishes policy.

| Decision | Approved / existing boundary | Proposed choice requiring explicit approval | Gate |
| --- | --- | --- | --- |
| Ticket creators | Only existing authenticated report/dispute intake is implemented; Batch 8A Admin Support is read-only. | Authenticated requester only initially; define suspended-user support obligations, general-account help and whether staff can ever create on behalf of another user. No unauthenticated/email-only intake by assumption. | Before 8B intake schema/endpoint deployment. |
| Categories | Reports/disputes keep their current semantics. | Candidate categories: rental assistance, listing safety/report follow-up, account access help, existing dispute follow-up. Approve exact codes, required relationship, unsupported categories and emergency guidance; no payment/credential recovery action implied. | Before permanent category registry. |
| Relationships | Booking participants, listing owner/reporters and dispute relations are server verifiable. | Per-category primary link requirements; whether unlinked tickets are allowed; validated same-case secondary links and handling deleted/changed relationships. | Before intake constraints and data migration. |
| Visibility / ownership | Owner–Support and Borrower–Support are separate private boundaries. No automatic transcript/evidence copying. | Approve requester-visible shared ticket fields, reporter anonymity, who sees a ticket's existence and one-party/non-booking channel membership. | Before participant-visible DTOs. |
| Conversation separation | Opposite participant cannot read the other channel; no automatic forwarding. Exact staff assignment/scope required. | Exact approved mediation selections, disclosure basis/consent/redaction, audience, duration and approval procedure. Routine sharing remains blocked-policy. | Before messaging or mediation. |
| Staff assignment / conflicts | No staff-role activation or legacy ADMIN bypass. Future independent human approval cannot use account aliases. | Who assigns/reassigns, conflict definitions and remediation, permitted channel subset, unassigned queue visibility and emergency staffing procedures. Support must not self-authorize broad scope. | Before assignments/grants, even in a real pilot. |
| Attachments / evidence | Existing booking/chat evidence protection stays independent. | Recommend text-only initial intake; approve any attachment formats/limits/scanning/retention and exact evidence-reference access. No import by default. | Before uploads or evidence linking. |
| Retention / erasure / holds | Preserve current immutable history. No speculative deletion schedule introduced. | Content/metadata/audit retention durations, lawful basis, deletion exceptions, legal holds, user requests, backup handling and authorization. Immutable audit must avoid retaining unnecessary narrative. | Before permanent model deployment. |
| Closure / reopen / escalation | Support closure never completes rentals, confirms receipt/inspection, sanctions users or resolves disputes. Support investigates and recommends. | Exact lifecycle states/transitions, closing authority/reason codes, requester disagreement, reopening versus new ticket, escalation routing and independent approval responsibilities. | Before lifecycle writer. |
| Notifications | No real email/live support delivery is currently configured. | Approved channels, opt-in/service notices, recipient resolution, content minimization, frequency, idempotency and delivery-failure behavior. | Before outbox/provider delivery. |
| Intake limits / duplicates | Existing listing-report duplicate policy remains specific to reports. | Rate limits, duplicate help requests, idempotency keys, case merging/provenance and abuse handling. Never automatically merge private channels. | Before public intake. |
| Auditing / database scope | 8A's operational metadata logs are not durable private-thread access audit. Existing private evidence reads retain their audit. | Approve exact staff audit actions/retention, fail-closed access behavior, trusted DB principal/context and scoped function/RLS architecture. | Before private staff/participant messaging or role rollout. |

Approval should identify decision ID/row, exact policy version, approved values, approver and review date in a controlled future change. This register contains no approval token and does not enable a feature. Unresolved gates block dependent work rather than prompting implementation to invent a default.

Support's eventual permitted work is assigned-case reading, scoped investigation, communication with the relevant participant, permitted private notes/events, recommendations and requests for separately authorized intervention. It does not include booking status editing, physical-custody repair, inspection approval, evidence alteration, serious sanctions, unsafe station restoration, staff grants or approval execution. Proposed role allocations in the capability registry remain specifications pending their respective approval/cutover gates.
