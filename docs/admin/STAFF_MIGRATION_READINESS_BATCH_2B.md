# Additive staff migration readiness — Batch 2B

24 October 2026 (Asia/Taipei). Design only: **no schema change, SQL migration, backfill, staff provisioning or cutover is executed in this batch**. Baseline `9b58969351fa091a969f7bca094f7a47c639fe5c` retains `UserRole`, `ChatReviewer`, sessions and all immutable history.

## Proposed additive records

| Proposed record | Minimum fields / constraints | Purpose and preservation |
| --- | --- | --- |
| StaffPerson | UUID, verified human identity reference, verification state/version, lifecycle state, created/reviewed times | A human, not an account. No automatic creation from ADMIN rows. Verification records are access-controlled and not copied into global audit DTOs. |
| StaffPersonAccountLink | personId, userId, validity window, verification provenance/version, revocation | Controlled binding of known account aliases to one person. Prevent overlapping links for an account; detect aliases during conflicts. Retain old bindings/history; person-link changes are sensitive reviewed changes, not a conflict reset. |
| StaffMembership | UUID, personId, exactly one fixed human role, ACTIVE/REVOKED/SUSPENDED/EXPIRED state, validFrom/expiresAt, authorizationVersion, policyVersion, approved request reference | One active membership per person/platform; do not union several roles to evade restrictions. A partial uniqueness constraint on ACTIVE membership plus transactional validity checks handles overlap; expired ACTIVE rows must be explicitly retired before replacement. No role inferred from UserRole or ChatReviewer. |
| StaffCapabilityGrant | membershipId, canonical capability/policy version, exact resource/domain scope, case/channel/audience constraints, validFrom/expiresAt, authorizationVersion, provenance/reviewer reference | Role eligibility AND explicit scope AND current domain constraints; grants can narrow roles, never add an unknown or role-ineligible capability. Default no grants. Wildcard/private evidence grants require separate design review and are not introduced by the current exact-resource policy. |
| StaffAuthorizationEpoch | person/membership version, current policy version, update reason/provenance | Monotonic DB-controlled invalidation on grants, role, identity-link or status changes. Never trust a cookie/body version as current authority. Multi-row changes use CAS/locking and advance versions atomically. |
| StaffSessionBinding | existing AuthSession reference, membership/person identifiers, authorization version, policy version, recent human step-up attestation and expiry | Preserve AuthSession rows/tokens and marketplace login. An old session without a binding has no new staff authority. Bindings are checked against current account, membership, epoch and policy each request; role claims do not authenticate staff. |
| StaffAssignment / EvidenceAccessGrant | case/resource/channel, person/membership, purpose, bounded evidence references, valid window/version and transfer provenance | Current chat assignedTo and historical decisions remain intact. New assignment history maps to old IDs without rewriting original evidence; current overlays/reassignments are explicit audited records. Separate Owner/Borrower private-channel grants; case assignment is not disclosure consent. |
| StaffAuthorizationEvent | actor/person/membership, action, scope reference, previous/new authorization versions, decision/provenance, timestamp | New append-only ledger with DB protections. Existing AdminAuditLog/ChatReviewer and immutable audit/evidence triggers stay untouched. Keep historical user IDs intelligible through references, not mass rewriting. |

Names/fields are proposed. Final relational constraints, RLS choices, retention and privacy rules require a separate schema review. Use UUIDs and foreign keys to existing records without changing existing IDs. Actor references should preserve both historical account ID and verified person identity for new events. Keep evidence bytes in their existing storage; grants reference bounded immutable evidence versions/hashes, not copied case bodies.

## Safe transition sequence

1. **Approve policy and human coverage.** Resolve the [capability matrix](ADMIN_CAPABILITY_MATRIX_BATCH_2B.md), especially temporary user restrictions, duration/cumulative caps, explicit booking actions, per-key settings, mediation disclosure and role-specific approval authority. Define staff identity proofing, MFA/step-up, emergency procedures and retention. Two aliases do not make two humans. No unilateral emergency exception to immutable invariants.
2. **Reconcile a restricted roster outside this implementation.** Review each legacy ADMIN and ChatReviewer grant separately. Record intended person, fixed role, scopes, reviewer eligibility, sponsor and independent reviewer. Do not publish rosters/secrets in repository docs. Unknown/unreviewed accounts receive no new membership. No ADMIN→Super Admin or enabled ChatReviewer→unrestricted Moderator backfill.
3. **Approve and test a new forward migration.** Add only new tables/indexes/FKs/events after reviewing historical checksums and backup/restore evidence. Seed no staff grants by migration. Verify on fresh and populated **owned disposable** fixtures that UserRole, AuthSession, ChatReviewer, assignments, audit rows, historical migration checksums and immutable evidence remain unchanged. Test partial migration/retry and constraint failures. Do not run against an existing user database in this batch.
4. **Build the trusted DAL and domain adapters.** Use the complete [legacy inventory](LEGACY_ADMIN_AUTHORIZATION_INVENTORY.md), including private listing media, CLI tooling and server-only helpers without actor checks. Replace every access path with current authorization plus resource scope and field-limited DTOs. Scope before filtering/counting; audit access before bytes; no client role/risk/policy flags. Revalidate writes and scope inside the same domain transaction; retain current locks, legal Booking transitions, original checklists/physical receipts, QR/GPS gates, evidence integrity and disputes.
5. **Continue shadow comparison without onboarding staff.** Supply independently validated snapshots from a reviewed DAL, monitor only bounded decision metadata (not bodies, GPS, tokens or raw grant payloads), and investigate mismatches. The Batch 2B MATCH result is deliberately not an authorization token; it has no activation flag. Build a separately reviewed enforcement API after all P/B allocations and domain gates are resolved. Do not silently rename MATCH to allowed.
6. **Prepare atomic cutover and bootstrap.** A specifically reviewed legacy cohort may continue existing behavior while replacement code is being prepared, but no new limited-role identity can use broad legacy ADMIN paths. Do not set USER.role=ADMIN to satisfy old wrappers. Replace every gate in the inventory and remove legacy bypasses atomically with enabling any new staff identity. No `ADMIN OR staffRole` fallback. A lower-privilege user remains denied by old endpoints throughout mixed-version rollout.
7. **Reconcile grants and sessions explicitly.** Current staff grants/status/assignment/identity must be rechecked on every privileged read/write. Revocation advances epochs and invalidates authorization immediately; caches must include person, membership, resource, grant, policy and authorization versions with bounded TTL and authoritative rechecks. Transactions lock/recheck actor and resource state; stale sessions do not retain authority. Test revocation while a request is in flight and failure of audit/DB/cache providers.
8. **Only then consider an approval engine in a separately authorized batch.** Store immutable requests and independent decisions bound to exact action, canonical payload hash, resource/evidence/policy versions and expiry. Require distinct currently authorized verified humans, exclude participants/targets/investigators/recommenders/original reviewers, require current step-up and current requester eligibility, and execute once with idempotency and atomic domain effect/audit. A proposal or approval capability is not execution authority. This batch implements none of those persistence/execution services.
9. **Retire compatibility and operational shortcuts.** Reconcile historical identities/grants without rewriting history. Replace local provisioning helper usage with the separately approved staff process. Recheck orphaned assignments and retain case holds when no eligible independent reviewer exists. Never silently assign the migration operator every private case.

## Bootstrap and small-team constraints

Initial provisioning needs an independently reviewed verified-person roster and protected out-of-band procedure. Staff-grant changes and Super Admin-authored high-risk requests need two independently eligible humans under the proposed SA allocation; one SA plus an OPS requester cannot approve the SA's own request or change staff grants. An appeal may require an additional eligible reviewer if the available humans are original investigators/participants. When coverage is insufficient, hold or reject the high-risk action and arrange authorized coverage; never use alternate accounts, service principals or a self-approval flag. Immediate station suspension remains a distinct deny-only authority after its policies are implemented, not permission to restore.

## Future service principals — design separation only

Reserve a discriminated principal model (`HUMAN` versus `SERVICE`) and separate future ServicePrincipal/ServiceCapabilityGrant/audit identity records. Do not assign human staff roles to agents or share a human session/cookie. Future narrowly scoped assistance might summarize explicitly granted evidence or suggest classifications, with bounded retention, provenance, model/version logs and human review. Any proposal/execution workflow needs separate authorization and human-approval design; service principals cannot count as either independent human. No service table, credential, production identity, autonomous task, external disclosure or AI right is implemented now; every AI contract and every service principal currently denies.

## Rollback and release gates

- Until cutover, rollback simply removes unused shadow modules/tests; current ADMIN/ChatReviewer access is unchanged.
- After future additive migration, rollback application behavior without dropping grant/history tables or rewriting legacy records. Revoke new staff access if an enforcement regression appears; **never** restore broad ADMIN markers or old bypasses to keep new staff working.
- Gate releases on exhaustive capability/role negatives, every legacy HTTP/service/page boundary, mixed versions, protected media, privacy projections/counts, alias conflicts, stale authorization, case/channel assignment, current grants, evidence-read audit failure, legal rental transitions and temporary-mode production exclusion.
- Migration/approval concurrency, step-up verification, trusted snapshot provenance and privacy DTO enforcement are **not implemented or proven** by the current in-memory shadow tests. They are blockers for activation, not implied guarantees.
- No execution of this plan, database migration, permission activation, merge or deployment is authorized by this document.
