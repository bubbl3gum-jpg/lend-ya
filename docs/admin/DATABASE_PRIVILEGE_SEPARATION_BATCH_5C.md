# Database privilege separation — Batch 5C candidate and evidence

24 October 2026 (Asia/Taipei). This is a **tested disposable candidate profile**, not an installed runtime credential change, production GRANT migration or new staff authorization system. The existing app/pilot still uses `lib/prisma.ts`'s configured connection. Do not describe the deployed application as privilege-separated on the strength of these tests.

## Five component principals

| Principal | Candidate rights | Forbidden / deployment conditions |
| --- | --- | --- |
| Ordinary runtime | Existing marketplace DML required by participant services, current-user auth/session persistence, SELECT official MRT catalogue, existing append-only legacy Admin audit INSERT | No schema ownership/CREATE, role grants, trigger disable, replication bypass, migration history, Staff* tables, MFA assurance/key insert or staff/approval authority. User role UPDATE denied; new-user INSERT restricted to USER by fixture RLS. |
| Controlled migrations | Own application schema/tables/functions; reviewed DDL only in an offline controlled path | Never a web-process credential. Can intentionally change protections: isolate secrets, execution identity and approvals. Production should prefer a NOLOGIN owner assumed only by a controlled migrator. |
| MFA verifier | Current authentication/verified identity reads; MFA key, challenge, version, rate-budget and assertion/event persistence | No marketplace role change, staff provisioning, approvals, general domain writes or DDL. Credentials belong to a separately isolated verifier process, not merely a second pool accessible to the ordinary runtime. |
| Protected authorization/audit writer | Bounded staff identity/authorization writes, invoker-trigger history maintenance and audit INSERT; activation restrictions remain enforced | Not a generic write API or audit(JSON) endpoint. No schema ownership, MFA proof manufacture, historical rewrite or activation override. Future use requires trusted identity/session/intent verification. |
| Operational inspection | Only a fixed security-barrier aggregate health view | No underlying User/Booking/evidence/key/assurance/audit tables, DML, credentials or arbitrary exports. |

`tests/support/database-principals.ts::principalFixture` installs this profile only after the existing effective-target and ownership checks. `tests/database-principals.test.ts` opens **separate actual PostgreSQL login connections**, verifies session_user=current_user and NOSUPERUSER/NOCREATEROLE/NOCREATEDB/NOBYPASSRLS, and tests forbidden SQL under those identities. This is not SET ROLE inside a superuser session, which would give a misleading role-escalation result.

Ephemeral roles are PostgreSQL **cluster-scoped objects**, even though all their explicit grants, objects and data operations target only the new owned test database. Each has an unpredictable generated password, a short test expiry, a run-specific name/comment, no role memberships and no replication rights. No existing role/credential is adopted or altered. Connections close and DROP OWNED / DROP ROLE run in finally, exclusively for the newly created roles and owned database. Production/shared-cluster use is not authorized; the local harness requires role-creation permission. An interrupted process can require explicit owned-run cleanup. A read-only catalog check at closeout verifies no test roles/databases remain.

Passwords/URLs are never emitted or committed; no password-authentication-strength claim is inferred from a local test server's pg_hba policy. Production must explicitly restrict CONNECT across databases and reject inherited PUBLIC access. The experiment does not alter pg_hba, production credentials, another database's grants or deployment infrastructure.

## Demonstrated rights and actual functionality

The ordinary runtime receives no protected-table privileges, no CREATE on public and no ability to SET ROLE to a writer/verifier/migrator. Attempts to create a table/trigger helper, disable protected triggers, use session_replication_role, truncate/rewrite Admin audits, promote/insert an ADMIN user, forge staff membership/approval or insert MFA assurances/keys fail. Direct epoch mutation fails. Official MRT catalogue DELETE fails; listing reads still work.

Runtime-authored USER registrations are accepted by actual Next routes; client role spoofing cannot promote. Actual login, HttpOnly session persistence, current-user lookup, public catalog read and logout/session invalidation succeed under the candidate runtime connection. `lib/auth.ts::persistSession` is additionally exercised using the restricted Prisma client. This proves those selected ordinary flows, not every existing application operation under the candidate profile. Full legacy regression suites still run separately through their normal owned harness.

The MFA principal runs the unchanged real cryptographic service with its restricted Prisma connection: native-protocol registration data and an actual ECDSA signed assertion produce factor assurance, never staff authority; authenticated revocation succeeds. It cannot change marketplace roles or insert staff membership. Immutable assurance history cannot be rewritten. The protected writer cannot activate a DRAFT membership, directly increment a trigger-maintained epoch, insert internal history directly, rewrite immutable Admin audit or create a COMMITTED security result. Existing approval suites separately verify APPROVED/EXECUTED/APPROVE blocking.

The inspector can read only a fixed aggregate view, not its underlying tables or keys. Only the migration principal can perform the controlled DDL probe. All 23 persisted migration names/checksums remain identical across the experiment.

## Row-lock privilege discovery

PostgreSQL requires UPDATE privilege for SELECT FOR SHARE used by `lib/authorization/mfa/service.ts::actor`. A naïve read-only identity grant therefore does not support the real verifier. Granting unrestricted identity UPDATE would be unsafe.

The candidate grants UPDATE only on each immutable identity **id** column of AuthSession, User, StaffPerson and StaffAccountAssociation, with a non-owner/non-disableable test trigger rejecting any actual MFA-principal UPDATE of that column. User RLS has a separate MFA SELECT policy, UPDATE visibility for locking and WITH CHECK(false) for writes. Other profile/role columns remain ungranted. Negative SQL tests attempt the guarded writes and prove rejection, while actual verification proves locks work. An initial profile lacked these lock/RLS permissions and failed; that was an integration finding, not a reason to grant ownership or weaken the verifier.

This fixture mechanism is not automatically approved as production DDL. Review either explicit immutable-column lock grants/guards or narrowly typed SECURITY DEFINER locking/read procedures owned by a dedicated NOLOGIN principal. The latter need fixed qualified objects/search_path, no dynamic SQL or caller-set identity variables, revoked PUBLIC EXECUTE, exact permitted callers and separate security review. No production definer function is added here.

## Audit insertion and remaining architecture

Current staff history functions are **invoker** triggers. Their writer needs explicit history/version privileges, while triggers reject direct insertion/update via depth/immutability checks. A non-owner cannot create a malicious helper trigger to spoof that depth. This is an additional engine protection, not a substitute for a trusted issuer or proof of cryptographic actor identity.

A runtime that can arbitrarily write to the same database as an assurance ledger can forge assurances. A verifier credential in the same compromised Next process is not a secure boundary. Production requires a separately isolated verifier identity/process/secrets, independently bound current session/person/origin verification and bounded response. The ordinary app must never obtain its persistence credential. The verifier itself remains a trusted issuer: possession of its database credential can fabricate assertion rows. Protect that credential and verify trusted issuance at every authorization consumer.

Likewise, an authorized audit writer can lie about actor attribution unless it verifies exact session, canonical person, versions, action/resource/purpose and approval intent. Do not expose a procedure accepting arbitrary actor IDs, JSON claims or a caller-controlled PostgreSQL session variable. Proposed first-read integration should make a typed scoped read plus validated audit insertion indivisible in a reviewed DB procedure or equivalent trusted transaction boundary. Giving runtime membership in the writer role or putting a writer password in runtime environment variables does not solve the problem. A separate audit connection cannot on its own supply same-transaction read/audit atomicity.

Legacy Admin functions currently insert AdminAuditLog through the common runtime connection. The fixture preserves INSERT for those operations and prevents rewrite/truncate; it does **not** solve forged legacy audit attribution by a compromised runtime. Splitting legacy domain mutations/audit requires a separate reviewed refactor. Current staff COMMITTED results stay forbidden, and the shadow evidence adapter's optional audit callback is not a production writer.

Further deployment requirements: explicit per-table/column allowlists rather than this experiment's schema-classification loops; reviewed default privileges for newly migrated objects; removal of PUBLIC schema CREATE/function EXECUTE; no untrusted schema extensions; per-database CONNECT/SSL policy; pool identity and role reset checks; encrypted/rotated component secrets; no runtime access to migration/verification/writer secrets; bounded lock/statement timeouts; audit retention/export and tested restore. The candidate's broad marketplace runtime reads are not a future lower-staff resource-scope policy. Do not reuse that identity or unrestricted Admin helpers as a staff read boundary.
