## Operational acceptance sequence

1. Approve domains/identity/recovery/staffing/retention and first-capability allocations. Record the actual values and accountable humans in a private deployment change, not guessed defaults in source.
2. Review privileges and isolated verifier/audit transaction architecture. Reproduce both positive application flows and negative principal tests under the final platform/authentication configuration. Current local PostgreSQL authentication is not evidence of production password/TLS strength. Verify role/default grants after every migration and secret rotation.
3. Stage an optional enrollment cohort using real device coverage and qualified support/recovery drill. Keep marketplace custody/return/inspection access available. Explicitly communicate factor assurance versus staff permission; no PENDING/shadow credential is accepted.
4. Exercise session swap/reuse, stale epochs/policies/grants, alias conflicts, logout, revoked/expired factor, cross-origin traffic, concurrent challenge consumption, audit/DB/outbox failure, retention access and rollback. No sensitive response may precede durable audit where required.
5. Independently approve any future staff read pilot and issuer. Only after those controls and recovery are operational should a separate reviewed change enforce MFA for existing Admin. Approval execution and serious sanctions remain separate later reviews.

Batch 5B's `passkeyPilotConfiguration` deliberately rejects NODE_ENV=production and any non-localhost realm; `proxy.ts` refuses its surfaces early. **Do not turn that gate off to ship production.** Implement the approved production composition in a separately reviewed batch with actual deployment values and end-to-end tests. No activation flag, production RP placeholder, live secrets or hidden emergency account is introduced here.
