# Staff read deployment boundary — Batch 6B

24 October 2026 (Asia/Taipei). Future requirements, not deployment authorization. Existing pilot remains synthetic, development-only and restricted to owned disposable databases.

## Reviewed implementation

`lib/staff-read-pilot/config.ts` checks explicit development mode, exact local origin, matching validated database URLs, run ID and database/schema ownership markers. `proxy.ts`, the page and API refuse production/disabled exposure. `bridge.ts` authenticates the actual session and checks runtime privileges; bounded fixed-command requests go to a private authenticated socket. `worker-service.ts` performs genuine WebAuthn verification; `read.ts` checks current identity, session birth, versions, proof, credential, exact grant, owner/alias conflicts and current resource under locks. Only `id`, `status`, `category`, `adminRestricted` are selected. Audit and final checks commit before the buffered response returns. There is no legacy Admin data-helper fallback.

The positive chain deliberately requires `OWNED_SYNTHETIC_HUMAN`, fixture `TEST_ACTIVE` records, a fixture policy and matching public DRAFT references. Those DRAFT references and real PENDING session records never independently authorize a real staff read. The fixture schema cannot become a production issuer. Existing ACTIVE/COMMITTED/APPROVE/APPROVED/EXECUTED prohibitions remain unchanged.

No confirmed new defect was found in this chain. Batch 6B changes the shared login form and test instrumentation, not staff admission/read/worker code. `tests/staff-read-pilot.integration.test.ts` remains the concrete 14-test HTTP/browser/service/DB regression; production/disabled refusal is also tested by `tests/mfa-pilot-production.test.ts`. Exact exits and artifacts are in [verification](../security/batch6b/verification.json).

## Concrete deployment requirements

| Boundary | Required implementation and release evidence |
| --- | --- |
| Runtime identity | Separate unprivileged OS/container service accounts for web runtime and privileged verifier/read service. No shared UID, supplementary group, host PID namespace, ptrace access, container socket, privileged capability or writable executable/module path crossing the boundary. Demonstrate denied process/environment/file access from an intentionally compromised runtime fixture. |
| Filesystem/secrets | Web image contains only runtime credential. Mount verifier and read/audit secrets exclusively into their service, outside web workspace, backups, build cache and logs; directory 0700 and secret 0400/0600 owned by that service. Operator/migration `.env` and owner credentials must not be readable by web or its deployment identity. Separate build and migration identities; no secrets in build args, command arguments, source or screenshots. Current same-user worker and operator `.env` do not meet this requirement. |
| Process startup | A restricted supervisor delivers secrets privately at startup, starts a pinned reviewed artifact and denies arbitrary commands/env/module injection. Worker must check expected DB identity/privileges and fail closed. Stdin bootstrap avoids argv leakage but alone does not defend shared UID/process inspection. |
| IPC | For same-host deployment, private socket directory and explicitly controlled service group, socket permissions limited to the intended peer, peer-identity check plus rotated authenticated protocol. Existing 0600 development socket is not a cross-UID deployment recipe. For separate containers/hosts, authenticated TLS service identities, no public ingress, bounded requests/timeouts, fixed schema/commands, replay/request binding and rate limits. Transport identity alone cannot assert staff authorization. |
| Database | Runtime: no ownership, CREATE, role membership, proof/grant/binding/audit writes or security-definer escape. Verifier: exact challenge/key/assurance writes only. Read/audit principal: exact current-authority reads, four-field Listing projection and typed append-only access events only. Provisioning and migrations are separate offline identities. Runtime must not possess either worker credential, regardless of separate SQL usernames. Verify effective roles, search paths, connection overrides and grants. |
| Audit integrity | Read/validation/audit/final checks/commit form one transaction, fail closed on insert/commit/timeout. Actor/resource/version attribution derives from authoritative rows, not arbitrary caller JSON. Enforce append-only UPDATE/DELETE/TRUNCATE protection, restricted writer, durability, backups and restricted evidence access. No private values or credentials in operational errors. External monitoring complements the authoritative transaction; it cannot substitute for a missing audit. |
| Rotation/revocation | Inventory versions, rotate one identity at a time, drain old pools and explicitly terminate old DB sessions: changing a password does not disconnect established sessions. Revoke old transport keys with a bounded overlap approved by security. Invalidate affected staff bindings/auth/MFA versions and stop issuance on compromise. Prove old credentials and existing pools cannot retain access. |
| Availability/monitoring | Bounded metadata counters for denial categories, worker timeout, audit failure, proof expiry, lock timeout and unexpected privilege changes; no raw SQL errors, cookies, proof bodies or private Listing fields. Alert named operators. Worker/audit outage returns denial/503 without cached reads or owner fallback. Recovery restores reviewed service, checks privileges and audit reconciliation, then allows a fresh explicit request. Never replay an operational mutation. |

## Acceptance drill

In a fresh isolated staging fixture: compromise only the runtime identity; attempt reads of worker secrets/process env, socket impersonation, arbitrary commands and SQL writes. Require denial and an attributable safe diagnostic. Stop verifier/read service and audit sink; verify no metadata or success record is returned. Rotate credentials and terminate existing sessions, revoke a staff session before read locks, and verify subsequent requests deny. Test a revocation waiting behind an already authorized read: the current model linearizes at commit; delivered metadata cannot be recalled. Obtain independent review of infrastructure manifests and actual deployed permissions, not just unit mocks.

No production configuration, secret, account or deployment was installed by this batch. Production trust isolation remains unproven and blocks rollout.
