## Proposed incremental cutover

1. **Resolve product policy first.** All production approval readiness currently denies, including SA allocations. Approve exact action taxonomy, allowed payload fields, risk, reviewer/executor roles, emergency procedure, TTL, revocation/staleness semantics, prior-reviewer lineage and one-reviewer versus quorum requirements. Frozen historical proposed arrays are not approval. Routine announcements/settings versus high-impact actions require precise boundaries.
2. **Complete trust and privacy.** Implement separately reviewed live staff-session/MFA issuer verification and protected actor provenance. Build current case/participant/subject/investigator/related-incident/alias mappings, secure immutable payload/reason/evidence providers and field-limited reviewer DTOs. Support remains investigation/escalation only for user restrictions; private Owner/Borrower channels remain separate.
3. **Prepare one domain at a time without activation.** Start with a narrowly specified sensitive action; add action-specific payload validators, locked resource/version checks, no-effect execution plans and negative tests. Preserve every caller from the complete legacy inventory, including direct service/CLI paths. Do not expose a parallel limited-role endpoint that calls broad ADMIN helpers.
4. **Design separate execution receipts and atomic effects.** Revalidate current requester/reviewer/executor authority, human assurance, conflicts, exact revision/hash/audience/policy/evidence and idempotency under a reviewed lock protocol. Apply only the explicit domain change with an immutable receipt and durable audit in one transaction. No generic execution callback and no approval-as-role/grant shortcut.
5. **Close every legacy bypass before claiming coverage.** Route both old HTTP and direct services through the reviewed domain boundary at the same cutover. Updating a page or creating an approval row while leaving `resolveDispute`/`moderateUser` direct paths available does not enforce approvals. Do not introduce `ADMIN OR staffRole`, grant ADMIN to lower roles, or silently exempt a legacy cohort.
6. **Independently review deployment/rollback.** Prove fresh/populated migration, backup/restore, mixed-version, negative authorization, lifecycle/physical evidence, idempotency, audit-outage and concurrency behavior. Only a separately authorized forward migration may reconsider blocked states. Roll back application behavior while preserving additive history; never drop/rewind approvals, sessions or old migrations.

## Outstanding decisions / Batch 4B gates

- [ ] Product-approved per-action role, requester/approver/executor and risk allocations; no real policy is currently enabled.
- [ ] Verified MFA issuer/assertion validation, replay/recency/recovery policy and human attestation provenance. PENDING and VERIFIED_FIXTURE are not production assurance.
- [ ] Production domain assignments, immutable payload/content verification, scoped reason/rationale/evidence stores and case lineage. The owned test payload table is not a production store.
- [ ] Request refresh/supersession when original requester binding/epoch or policy changes; complete cancellation/expiry/rejection/quorum policy. The fixture contract conservatively permits one decision per revision and excludes earlier revision reviewers.
- [ ] Distinct human coverage for requester/reviewer and staff-bootstrap conflicts. With only two humans, a changed revision may require another eligible reviewer under the conservative prior-reviewer rule. Hold work if coverage is insufficient; aliases/new request IDs/service agents cannot bypass conflict lineage.
- [ ] Minimal runtime versus migration/audit DB privileges; no runtime ownership, trigger creation, constraint disabling, arbitrary history writes or SECURITY DEFINER shortcut. DB owners can bypass current protections; no production credential changes were made here.
- [ ] Retention/legal holds, immutable archival/pseudonymization and account-link correction without erasing conflict history. No retention period or destructive purge is assumed approved.
- [ ] Complete global lock ordering and requester/approver/resource/assignment/blob consistency, deadlock/timeouts, external-store failures, caches and transport/revocation review. Audit failure must never grant access or effect.
- [ ] Separate typed execution/receipt design and an explicit later authorization to implement it; no executor is authorized by Batch 4A or this checklist.

Batch 4B should remain a reviewed preparation batch unless the product owner separately authorizes a narrower activation milestone. This document grants no permission to activate memberships, issue live sessions, migrate existing databases or deploy.
